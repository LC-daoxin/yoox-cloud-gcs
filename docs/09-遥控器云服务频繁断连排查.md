# 遥控器云服务频繁断连排查

本文用于处理 Autel Enterprise 遥控器 APP 中“云服务已连接 / 未连接”频繁切换的问题。

## 1. 安全原则

如果飞机正在飞行：

- 不要重启遥控器、Autel Enterprise APP、MQTT Broker 或云端服务。
- 不要连续切换云服务开关或反复点击重连。
- 优先使用实体遥控器接管并安全降落。
- 只有确认飞机已经落地且飞行模式为待机后，才能执行 APP 重启和连接清理。

## 2. 典型现象

- 遥控器 APP 每隔数秒显示一次“云服务已连接”，随后又显示“云服务未连接”。
- APP 日志重复出现整套 MQTT Topic 订阅。
- APP 日志先出现订阅成功，紧接着出现 `not connected`。
- APP 日志出现 `connectionLost`、`EOFException` 或 MQTT 错误码 `32109`。
- 服务端反复收到 `update_topo`，设备上下线事件被频繁触发。

## 3. 本次确认的根因

同一个遥控器 APP 进程创建了多个 MQTT 连接，并且这些连接使用相同的 Client ID。

MQTT Broker 同一时间只能保留一个相同 Client ID 的在线连接。新连接建立后，EMQX 会以
`reason: {shutdown,takenover}` 关闭旧连接。APP 收到 EOF 后再次自动重连，新的连接又把当前连接
挤下线，最终形成循环。

这类问题不是简单的网络中断。只看“当前客户端 connected=true”不足以判断连接健康，必须检查
`connected_at` 是否持续变化，以及 Broker 是否出现 `takenover`。

## 4. 快速恢复流程

### 4.1 确认飞机已落地

在座舱中确认飞机处于待机，或者检查最新 OSD 的 `mode_code`。只有 `mode_code=0`（待机）时才继续。

不要仅凭速度为 0 判断已经落地。

### 4.2 确认 ADB 已连接

```bash
adb devices -l
```

设备状态应为 `device`，不能是 `offline` 或 `unauthorized`。

### 4.3 完整重启遥控器 APP

```bash
adb shell am force-stop com.autel.enterprise
adb shell monkey -p com.autel.enterprise -c android.intent.category.LAUNCHER 1
```

第二条命令必须使用 APP 的标准桌面入口。不要直接启动
`com.autel.cloudapi.ui.CloudApiServiceActivity`，该 Activity 未导出，ADB 会返回权限错误。

APP 启动后等待其自动恢复云服务，不要连续点击云服务开关。

### 4.4 验证恢复结果

```bash
APP_PID=$(adb shell pidof com.autel.enterprise | tr -d '\r')
adb logcat -d -v threadtime --pid="$APP_PID" \
  | grep -Ei 'connectionLost|not connected|EOFException|connectComplete'
```

恢复后的预期结果：

- APP 不再重复出现 `connectionLost`。
- EMQX 中该 Client ID 只有一个在线连接。
- `connected_at` 保持不变，而不是每隔几秒更新。
- 服务端不再高频收到 `update_topo`。

## 5. 进一步诊断

### 5.1 读取 APP 当前页面和进程

```bash
adb shell dumpsys window | grep -E 'mCurrentFocus|mFocusedApp'
adb shell pidof com.autel.enterprise
```

### 5.2 查看 APP 的连接日志

```bash
APP_PID=$(adb shell pidof com.autel.enterprise | tr -d '\r')
adb logcat -d -v threadtime --pid="$APP_PID" \
  | grep -Ei 'mqtt|cloud|connect|disconnect|EOFException|socket|not connected'
```

不要把包含账号、密码、Token、设备密钥或完整设备序列号的原始日志直接发到群聊或工单。分享前先脱敏。

### 5.3 判断是否为 Client ID 抢占

在 EMQX Dashboard 为遥控器 Client ID 创建短时客户端追踪，并隐藏消息 Payload。重点检查：

```text
emqx_connection_terminated, reason: {shutdown,takenover}
```

如果短时间内出现多个来源端口的 `CONNECT`，并且每次都伴随 `takenover`，即可确认是重复连接实例。

以下信息也能辅助判断：

- `clientid_registration_throttled`：连接创建过于频繁，Broker 已开始限流。
- `server_busy`：频繁抢占期间，新连接被临时拒绝。
- `packet_identifier_inuse`：持久会话中还存在未完成的 QoS 2 报文状态。

## 6. Broker 侧预防配置

项目的 `deploy/emqx/base.hocon` 已配置：

```hocon
mqtt {
  session_expiry_interval = 0s
}
```

该配置让 MQTT 3.x 客户端断开后立即清理会话，避免下次连接恢复旧的 QoS 2 报文状态。

注意：该配置只能处理断线后的残留会话，不能阻止多个仍存活的连接使用同一个 Client ID 互相抢占。
发生 `takenover` 时，仍需清理 APP 内的重复 MQTT 客户端实例。

## 7. 不建议的处理方式

- 飞行中重启 APP、遥控器、Broker 或 API。
- 连续点击云服务开关或重连按钮。
- 只删除 Broker 会话，但不清理 APP 中的重复连接实例。
- 为了避免抢占而随意修改设备 Client ID；设备 Topic、ACL 和身份关联可能因此失效。
- 未脱敏就保存或发送 ADB、MQTT、HTTP 登录日志。

## 8. 仍未恢复时需要收集的信息

如果完整重启 APP 后仍然复现，记录并提供：

1. 故障发生的准确时间，精确到秒。
2. 飞机当时是否在地面，以及最新 `mode_code`。
3. APP 新进程的 `connectionLost` 前后约 20 秒日志（完成脱敏）。
4. EMQX 同时间段的客户端追踪，重点保留 `CONNECT`、`CONNACK` 和断开原因。
5. 同一设备 SN 是否同时登录了其他遥控器、模拟器或测试程序。
6. APP 完整重启后，EMQX 的 `created_at`、`connected_at` 是否仍持续变化。

## 9. 本次处理结果

本次执行了以下操作：

- 通过 ADB 确认 APP 日志中存在 `EOFException` 和重复订阅。
- 通过 EMQX 客户端追踪确认断开原因为 `takenover`。
- 确认飞机处于 `mode_code=0` 后完整重启 Autel Enterprise APP。
- 将 MQTT 3.x 会话过期时间设置为 0 秒，避免旧 QoS 2 状态跨重连保留。
- 重启后的观察窗口内，`takenover=0`、协议错误为 0、APP `connectionLost=0`。
