# Mac 端 RTSP 硬解与平滑播放

更新日期：2026-10-27。事实来源：`scripts/play-rtsp-mac.py`、本机实时拉流验证。

## 适用情况

网页 WebRTC 正常，但 VLC / ffplay 停顿或积压，且已确认 RTSP 时间戳与实际收帧节奏不一致。
本次实测输入为 H.264、960×720，稳定区间实际接收约 29.99 fps；原始视频时间戳
每帧约递增 370 ms。450 帧采样没有解码错误，但帧到达间隔 P95 约 70 ms，
最大约 379 ms，说明时间戳异常和到达抖动都需要处理。
这些数据来自本次测试，不是所有设备、网络或镜头的固定参数，也不证明异常由某个组件单独造成。

本机 ffplay 8.0.1 为关闭编译优化的调试构建，缺少直接 `-hwaccel` 所需的 Vulkan 渲染。
脚本使用 FFmpeg 的 VideoToolbox 解码，将原始像素经有界内存队列送给 ffplay。
播放时间由配置帧率生成，避免继承异常的媒体时间戳。

## 使用

需要 macOS、Python 3，以及 PATH 中可用的 FFmpeg / ffplay，FFmpeg 必须支持 VideoToolbox。
在仓库根目录运行，将地址换成实际的 RTSP 拉流地址：

```bash
python3 scripts/play-rtsp-mac.py \
  'rtsp://<nano-ip>:8554/<drone-sn>-<payload-index>' \
  --size 960x720 --fps 30 --buffer-ms 100
```

默认尺寸为本次验证流的 960×720；其他分辨率请修改 `--size`。脚本会缩放到该尺寸，
因此应填写与实际输入一致的宽高以保持原画质和宽高比。`--fps` 应匹配实际接收帧率，
不要依赖异常流中的帧率元数据。该脚本仅播放视频，不播放音频，不录制视频文件。

默认先缓存 3 帧，约 100 ms，再按 30 fps 定时送出。队列上限为 6 帧，积压时丢弃旧帧；
临时断粮时重复上一帧；本机调度落后时加速送出，保留全部时间轴位置，让播放器按外部时钟
追帧，避免原始像素流的隐含帧编号时钟逐渐落后。这些机制限制内存与积压，不能保证任意
网络条件下零卡顿或固定端到端延迟。超过缓冲能力的停顿仍可能表现为重复画面。

- 延迟优先可试 `--buffer-ms 50`，但抗抖动能力会下降。
- 网络波动较大可试 `--buffer-ms 300`，会增加起始缓冲延迟。
- 默认 `--sync ext` 使用外部时钟追帧；`--sync video` 仅供对照测试，可能让画面持续落后。
- 在播放窗口按 `q`，或终端按 Ctrl+C 退出；退出时会清理本次解码和播放子进程。
- 连接断开或解码器退出后脚本结束，需要重新运行；不会重启 Nano 或设备推流。

这只是客户端播放处理，不需要启用 `compose.transcode.yml`，不修改网页、服务端或飞控状态。

## 验证与日志

可用 `--duration 60` 进行一分钟测试。默认每次创建独立临时日志目录并打印位置；
也可以通过 `--log-dir <directory>` 指定目录，该目录下的同名日志会被覆盖。

退出后生成 `stats.json`：

| 字段 | 含义 |
| --- | --- |
| `received` | 从解码器接收的完整原始视频帧数 |
| `sent_frames` | 送入 ffplay 的帧数，不等同于实际渲染数 |
| `repeated` | 队列暂空时重复上一帧的次数 |
| `discarded` | 缓冲或调度处理丢弃的旧帧数 |
| `scheduler_late_ticks` | 本机调度落后超过一帧、需要追赶的送帧次数，不代表丢失时间槽 |
| `renderer_dropped_frames` | ffplay 的 `fd` 丢帧计数，未取得统计时为 null |

`decode.log` 用于检查解码错误，`play.log` 保存播放器统计。不要只看 `fd=0` 判断成功：
还应确认持续送帧、没有大量重复或缓冲丢弃，并观察播放画面。

## 2026-10-27 验证记录

同一路实时流的顺序短时对照（网络和画面随时间变化，并非完全相同的录制输入）：

| 播放方式 | 测试时长 | ffplay 丢帧 |
| --- | --- | --- |
| 接收时间戳 + fps 滤镜的原管道命令 | 约 35 秒 | 56 |
| 连续帧号时间戳 + 视频时钟 | 约 35 秒 | 16 |
| 初版有界帧缓冲脚本，300 ms | 约 35 秒 | 3 |
| 最终版，100 ms、外部时钟、保留时间轴追帧 | 约 60 秒 | 0 |

初版 300 ms 脚本该次接收 1053 帧，送出 1046 帧，重复 0 帧，缓冲/调度丢弃 4 帧，
调度跳过 4 个时间槽。用户反馈画面不卡，但延迟明显增大。后续复测发现调度跳帧还会导致
原始像素流时间轴落后，因此最终版改为保留时间轴的追帧逻辑，并将默认缓冲降至 100 ms。

最终版 60.05 秒测试接收 1791 帧，送出 1801 帧，重复 13 帧，队列丢弃 1 帧，
有 4 次调度追赶，ffplay 丢帧为 0。启动 2 秒后记录的播放器主时钟与视频时钟差最大约 7 ms，
末次约 1 ms；这不是端到端延迟测量。重复帧和丢帧统计不能相加当作总丢帧数。
结果支持短时改善，不代表任意现场网络下无卡顿；没有测量玻璃到玻璃的端到端延迟。
仓库 `make verify` 已通过；播放器参数、退出信号与统计处理的后续修改另行经过实时播放、
Python 语法和参数校验。该客户端脚本的验证阶段没有部署或重启 Nano；后续针对 VLC 的
服务端修复见 [RTSP 时间戳异常定位与服务端修正](23-RTSP时间戳异常定位与服务端修正.md)。
