# YOOX Cloud GCS 部署与运维指南

## 1. 部署前检查

- Linux x86_64/arm64 主机，Docker Engine 24+，Compose v2。
- 核心栈建议 4 核、8 GB 内存、30 GB 系统盘；媒体和对象存储使用独立数据盘。
- 主机时间同步，时区明确，DNS 和证书可用。
- 设备网络可达 Pilot 网关 9000、MQTT 1883、RTSP 8554；浏览器可达 Web 入口和 WebRTC UDP 8189。
- `.env` 已替换所有示例 Secret，`YOOX_PUBLIC_HOST` 不是回环地址。
- 已取得上云应用 ID、Key、License 和对应设备/固件授权。

执行：

```bash
cp .env.example .env
docker compose --env-file .env config --quiet
docker compose --env-file .env pull
docker compose --env-file .env build
docker compose --env-file .env up -d --wait --wait-timeout 300
```

## 2. 启动验收

```bash
docker compose --env-file .env ps
docker compose --env-file .env logs --tail=200 api
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/actuator/health
curl -sS http://127.0.0.1:9000/manage/api/v1/login
curl -fsS http://127.0.0.1:8081/healthz   # 在线 API 文档门户
```

验收顺序：

1. 所有核心容器为 `running/healthy`，三个 init 容器为成功退出。
2. Web 登录，默认工作空间正确。
3. Pilot/设备登录并连接 MQTT，设备拓扑出现。
4. OSD、state、HMS 持续更新。
5. 选择 `live_capacity` 中的视频源，以标清启动 RTSP，浏览器出现首帧；多设备 A→B→A
   切换时确认 A 的 MediaMTX publisher 未被停止且切回后直接复用。
6. 在授权测试条件下首次进入 DRC，确认同一 MQTT 会话能收到 `heart_beat` 回包，或连续零杆
   `drone_control` 双帧零杆探针（首轮通常 `seq=0→1`）均返回 `result=0`，无需第二次点击；
   丢包重试时同一零向量序号应继续递增，再验证排他控制、返航、退出和断网收敛。
7. 上传 KMZ、创建任务，分别验证执行、暂停、恢复、运行中取消和暂停中取消，并检查进度及媒体回传。

## 3. 日常服务巡检与状态查询

所有命令均在项目根目录执行，并默认使用根目录下的 `.env`。

### 3.1 快速巡检

日常检查先执行：

```bash
make ps
make smoke
```

- `make ps` 查看正在运行的 Compose 服务。
- `make smoke` 依次检查 Web 健康页、API Actuator、OpenAPI 契约、Pilot 登录路径和 WebSocket 路径。
- 两条命令均无报错退出，才表示容器状态和关键 HTTP 链路均通过。

需要同时查看已退出的一次性初始化任务时，执行：

```bash
docker compose --env-file .env ps --all
```

状态判定：

| 容器类型 | 正常状态 | 异常状态 |
| --- | --- | --- |
| `api`、`web`、`api-portal` | `Up ... (healthy)` | `unhealthy`、`Restarting` 或 `Exited` |
| `mysql`、`redis`、`minio` | `Up ... (healthy)` | `unhealthy`、`Restarting` 或 `Exited` |
| `emqx`、`mediamtx` | `Up ... (healthy)` | `unhealthy`、`Restarting` 或 `Exited` |
| `mysql-init`、`minio-init`、`emqx-init` | `Exited (0)` | 非 0 退出码或持续重启 |

`Exited (0)` 表示一次性初始化任务已成功完成，不需要将其保持在运行状态。

### 3.2 手工验证关键端点

```bash
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/actuator/health
curl -fsS http://127.0.0.1:8080/v3/api-docs | head
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/manage/api/v1/login
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/api/v1/ws
curl -fsS http://127.0.0.1:8081/healthz
```

预期结果：

- `/healthz` 返回 `ok`。
- `/actuator/health` 包含 `"status":"UP"`。
- `/v3/api-docs` 返回包含 `openapi` 的 JSON。
- Pilot 登录路径返回 HTTP `200`。
- 未升级协议的 WebSocket 探测返回 HTTP `400`，表示路由已存在。
- API 文档门户 `/healthz` 返回成功。

如果 `.env` 修改了 `YOOX_HTTP_PORT` 或 `YOOX_PILOT_PORT`，应使用实际端口；`make smoke` 会自动读取这两个配置。

### 3.4 日志查询

查看全部服务最近 200 行并持续跟踪：

```bash
make logs
```

按 `Ctrl+C` 退出日志跟踪，不会停止容器。只查看指定服务时：

```bash
docker compose --env-file .env logs --tail=100 api
docker compose --env-file .env logs --tail=100 web
docker compose --env-file .env logs --tail=100 emqx
docker compose --env-file .env logs --tail=100 mediamtx
docker compose --env-file .env logs -f --tail=200 api web
```

查询异常时，建议先记录当前容器状态，再检查相关服务日志，避免立即重启导致现场信息丢失。

### 3.5 启停、重启与重建

任何会重启 `api`、`web`、MQTT、Redis 或 MediaMTX 的维护都必须先通过飞行安全闸：安排维护窗口，
确认所有飞机已安全落地、现场人员可随时接管，最新 OSD 不处于起飞、飞行、返航或降落状态，并确认
没有正在进入/退出的 DRC。以下只读命令只显示各类活动键数量，不输出设备或任务标识：

```bash
docker compose --env-file .env exec -T redis sh -ec '
for pattern in "drc:session:*" "drc:state:*" \
  "wayline_job_running:*" "wayline_job_paused:*" \
  "control:point-flight:active:*"; do
  count=$(redis-cli -a "$YOOX_REDIS_PASSWORD" --no-auth-warning \
    --scan --pattern "$pattern" | wc -l | tr -d " ")
  printf "%s %s\n" "$pattern" "$count"
done'
```

所有数量必须为 `0`，且 OSD/现场同时确认没有返航、降落或其他飞行动作，才可执行下面的命令。
Redis 只是安全闸的一项证据，不得用手工删除活动键来“通过”检查；任一状态不确定就延期维护。

```bash
# 启动或更新全部服务，等待健康检查
make up

# 只重启 API
docker compose --env-file .env restart api

# 重建并更新 API 和 Web
docker compose --env-file .env up -d --build api web

# 启用监控 profile
make up-monitoring

# 停止并删除容器和网络，保留命名卷
make down
```

服务操作完成后再次执行 `make ps` 和 `make smoke`。不要用
`docker compose down -v` 做普通停机；`-v` 会删除命名卷中的数据库、对象和监控数据。

### 3.6 异常状态快速处理

1. 执行 `docker compose --env-file .env ps --all` 确认异常服务。
2. 执行 `docker compose --env-file .env logs --tail=200 <service>` 保留最近日志。
3. 检查 `.env`、端口占用、磁盘空间、Docker 资源和依赖服务。
4. 根据日志修正配置或依赖，然后只重启受影响服务。
5. 执行 `make smoke` 进行恢复验证。

常见业务故障的定位入口见第 7 节。

## 5. 备份与恢复

备份前记录镜像版本和 `.env` 的安全副本。数据库使用逻辑备份：

```bash
docker compose --env-file .env exec -T mysql \
  sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysqldump -uroot cloud_sample --single-transaction --routines --events' \
  > yoox-cloud-sample.sql
```

实际执行时密码应通过安全方式提供，避免写入 shell 历史。Redis 使用 AOF 卷，MinIO 使用
`mc mirror` 同步到独立存储。仅备份 Docker 卷目录不足以保证 MySQL 一致性。

恢复必须先在隔离环境验证。恢复顺序：MySQL → Redis（如需保留短时状态）→ MinIO → API →
Web；DRC 临时租约和短时令牌不应跨灾难恢复继续使用。

## 6. 升级和回滚

1. 备份数据库和对象存储。
2. 执行 `make verify`，并在测试环境运行 API、RTSP、DRC 和航线回归。
3. 按 §3.5 通过飞行安全闸；任一 DRC、航线、点飞、返航或降落仍活动时延期升级。
4. 拉取固定版本镜像，执行 `docker compose config --quiet`。
5. 滚动替换无状态 Web/API；涉及数据库变更时按迁移说明执行。
6. 执行 `make ps && make smoke`，再观察错误率、MQTT 断线、直播首帧、DRC 延迟和容器重启。

回滚只允许回到与数据库 Schema 兼容的版本。生产镜像不得使用 `latest`。

## 7. 故障定位

| 症状 | 首要检查 |
| --- | --- |
| Web 502 | `api` 健康、Nginx 日志、MySQL/Redis |
| 设备不上线 | 公网 1883、EMQX 用户、应用 License、Topic ACL |
| 遥控器云服务反复连接/断开 | 检查相同 Client ID 抢占；参见[遥控器云服务频繁断连排查](09-遥控器云服务频繁断连排查.md) |
| 有设备无视频源 | `live_capacity`、相机/负载能力、固件 |
| RTSP 已推无画面 | MediaMTX publisher、WHEP 请求、H.264、UDP 8189/TURN |
| Mac/Docker Desktop 下设备推流失败 | Docker Desktop 的 UDP 端口转发不可靠；须在 `.env` 中设置 `YOOX_RTSP_TRANSPORTS=tcp`，Nano 等 Linux 主机保持默认 `udp,tcp` 即可 |
| 切换设备后原直播停止 | 浏览器切换只应断开 WHEP reader；检查是否误调用 `/live/streams/stop`，以及 publisher key 是否按 `drone_sn/payload_index` 隔离 |
| DRC 连接拒绝 | 设备在空、控制权、任务状态、JWT Secret、Redis ACL |
| DRC 进入/重连后 ♥ 一直 0ms，无任何报错 | 在浏览器「◫ 日志」面板确认 `drc/up` 收到 `drone_control` 但不认。根因：EVO RC 固件的 `drone_control` ACK 恒返回 `output.seq=0`（不回显发送的 seq），若探针匹配强依赖 seq 则永远失败。应优先用 tid/bid 匹配，只有完全不带 tid/bid 的回包才退回 seq 验证 |
| 首次进入 DRC 一直等待、第二次才正常 | 检查浏览器交互日志中 `heart_beat` 与连续全零 `drone_control`；首轮通常为 `seq=0→1`，丢包重试必须继续递增而不能回放。部分 RC 不回显心跳，两帧当前会话 ACK 均确认后才开放控制，丢包应自动重试而非再次点击 |
| 一键返航/取消返航报 `211001`，但 `flight_authority_grab` 正常 | **EVO RC 实测（2026-08-12 MQTT 直连 A/B 验证）**：`return_home` 必须发送 `data:{}`（空对象）并携带 `device_list:[{sn:无人机SN}]`，固件才回复；`data:null` 的任何写法（带或不带 device_list）都被静默丢弃 → 211001。离线文档"data 为 null、不带 device_list"与实机不符，以实测为准 |
| API 重启后所有 services 指令报 `210001` | SDKManager 是内存注册表；API 重启后 `ApplicationBootInitial` 从 DB 恢复注册，若注册后被 `GlobalScheduleService`（每 30s，`expire≤30` 即 logoutDevice）误判离线再次清除，应确认 `registrationRecovery` 钩子已注入（可在日志中搜索 `Re-registered gateway`），以及 `online:*` Redis key 的 TTL 是否由 OSD 正常续期 |
| 控制指令约 9 秒后报 `211001` | 设备已收不到或未回复 `services_reply`；检查网关/子飞机在线、RC 下行 `device_list`（`takeoff_to_point`/`fly_to_point` 需要，`return_home`/`flight_authority_grab` 不需要）、MQTT Topic 与固件状态，结果未知时先查任务状态 |
| 航线失败 | KMZ/WPML、设备型号、负载、返航高度、电量、时间同步 |
| 航线暂停/恢复/取消提示状态不匹配 | 按 `job_id` 核对状态 `2/6/1/4`，检查网关运行与暂停 Redis key；执行中取消应先收到 pause 确认再 undo，成功/失败终态不可取消；已取消任务的重复取消只做幂等缓存收敛，超时后先刷新任务列表和进度事件 |
| 媒体无回传 / 航线 `314004` 失败 | STS、MinIO endpoint 是否对设备可达（容器内部主机名如 `minio:9000` 设备无法解析，须在 `.env` 中设置 `YOOX_MINIO_EXTERNAL_ENDPOINT=http://<主机IP>:9100`）、Bucket、设备到对象存储网络 |

## 8. 安全基线

- 上线前修改 Web 初始化密码和所有 `.env` Secret。
- 使用 TLS/WSS，限制 MQTT/RTSP 源 IP，管理端口不出公网。
- 每次远控前完成安全检查单，设置控制租约、心跳超时和现场接管方案。
- 不在日志中记录 JWT、MQTT 密码、MinIO 签名 URL 或完整上云凭据。
- 定期做依赖、镜像、配置和弱口令扫描。
- 真机飞行必须遵守当地法规、空域授权和组织安全流程。
