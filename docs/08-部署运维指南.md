# YOOX Cloud GCS 部署与运维指南

> 状态：当前运行手册
>
> 适用版本：1.10.0
>
> 更新日期：2026-10-22

本文用于维护已经部署在 Jetson Nano 上的 YOOX Cloud GCS。当前标准目录为：

```text
/home/jetson/yoox-cloud-gcs
```

首次安装、离线更新和镜像导入见 [Nano 完全离线快速部署](13-Nano快速部署.md)；环境变量的完整定义见
[配置指南](06-配置指南.md)。不要在 Nano 上构建源码或在线拉取镜像。

本文所有 Nano 命令都同时加载以下两个文件：

```text
compose.yml
compose.nano.yml
```

只加载 `compose.yml` 会丢失 Nano 的内存和 CPU 限制。普通 Linux 源码部署不使用
`compose.nano.yml`，请参照 [Linux 本地构建与部署](11-Linux本地构建与部署.md)。

## 1. 登录并进入项目目录

从 Mac 连接：

```bash
ssh jetson@<Nano-IP>
```

登录后必须先进入项目目录：

```bash
cd /home/jetson/yoox-cloud-gcs
pwd
ls -l .env compose.yml compose.nano.yml
```

`pwd` 应输出：

```text
/home/jetson/yoox-cloud-gcs
```

如果提示符仍为 `jetson@yahboom:~$`，当前目录是 `/home/jetson`。此时执行
`--env-file .env` 会寻找 `/home/jetson/.env`，并出现：

```text
Couldn't find env file: /home/jetson/.env
```

不要在错误目录中执行 `nano .env`，否则会新建一个无效的 `.env`。

## 2. Docker 服务检查

检查 Docker 是否运行并已设置开机启动：

```bash
systemctl is-active docker
systemctl is-enabled docker
docker version
docker compose version
```

正常结果应包含：

- Docker 状态为 `active`；
- 开机启动状态为 `enabled`；
- Docker Client 和 Server 都能显示版本；
- Compose 为 v2。

Docker 未启动时执行：

```bash
sudo systemctl enable --now docker
sudo systemctl status docker --no-pager
```

如果当前用户没有 Docker 权限，命令会出现 `permission denied`。应由管理员将用户加入 `docker`
组并重新登录，不要长期依赖权限过大的临时脚本。

## 3. 日常巡检

### 3.1 容器状态

```bash
cd /home/jetson/yoox-cloud-gcs

docker compose \
  --env-file .env \
  -f compose.yml \
  -f compose.nano.yml \
  ps --all
```

状态判定：

| 容器类型 | 正常状态 | 异常状态 |
| --- | --- | --- |
| `api`、`web`、`api-portal` | `Up ... (healthy)` | `unhealthy`、`Restarting`、`Exited` |
| `mysql`、`redis`、`minio` | `Up ... (healthy)` | `unhealthy`、`Restarting`、`Exited` |
| `emqx`、`mediamtx` | `Up ... (healthy)` | `unhealthy`、`Restarting`、`Exited` |
| `mysql-init`、`minio-init`、`emqx-init` | `Exited (0)` | 非 0 退出码或持续重启 |

三个 `init` 容器是一次性初始化任务，`Exited (0)` 表示成功，不需要保持运行。

### 3.2 HTTP 健康检查

默认端口下执行：

```bash
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:19000/actuator/health
curl -fsS http://127.0.0.1:8081/healthz
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/manage/api/v1/login
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/api/v1/ws
```

预期结果：

- Web 和 API Portal 的 `/healthz` 返回 `ok`；
- Actuator 返回包含 `"status":"UP"` 的 JSON；
- Pilot 登录路径返回 HTTP `200`；
- 未执行 WebSocket Upgrade 的探测通常返回 HTTP `400`，表示路由存在。

如果 `.env` 修改了端口，应使用修改后的实际端口。

### 3.3 日志、资源和磁盘

查看指定服务最近日志：

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml logs --tail=200 api
docker compose --env-file .env -f compose.yml -f compose.nano.yml logs --tail=200 emqx
docker compose --env-file .env -f compose.yml -f compose.nano.yml logs --tail=200 mediamtx
```

持续跟踪日志：

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml logs -f --tail=200 api web
```

按 `Control+C` 退出日志跟踪，不会停止容器。资源和磁盘检查：

```bash
docker stats --no-stream
docker system df
df -h
free -h
```

发现故障时先保存容器状态和日志，再决定是否重启，避免丢失现场信息。

## 4. 修改 `.env` 配置

### 4.1 修改前确认和备份

```bash
cd /home/jetson/yoox-cloud-gcs
pwd
stat -c '%n permissions=%a owner=%U:%G' .env

ENV_BACKUP=".env.bak.$(date +%Y%m%d-%H%M%S)"
cp -p .env "$ENV_BACKUP"
printf 'Backup: %s\n' "$ENV_BACKUP"
```

`.env` 应属于 `jetson:jetson`，权限应为 `600`。查看变量名但隐藏变量值：

```bash
sed -n 's/^\([A-Za-z_][A-Za-z0-9_]*\)=.*/\1=<redacted>/p' .env
```

不要把 `.env` 内容粘贴到聊天、工单或公开日志中。

### 4.2 使用 Nano 编辑

```bash
nano .env
```

Nano 常用按键：

- 方向键：移动光标；
- `Control+W`：搜索变量；
- `Control+O`，再按 `Enter`：保存；
- `Control+X`：退出；
- `Control+X` 后按 `N`：放弃未保存的修改。

环境变量使用 `KEY=value` 格式，等号两侧不要随意加空格。新增或修改变量时以 `.env.example` 和
[配置指南](06-配置指南.md) 为准。

### 4.3 常见配置类别

| 类别 | 典型变量 | 变更注意事项 |
| --- | --- | --- |
| 对外地址 | `YOOX_PUBLIC_HOST`、`YOOX_PUBLIC_RTSP_HOST`、`YOOX_DRC_MQTT_HOST` | 必须是遥控器或浏览器可达的地址，不能使用容器内部主机名 |
| MinIO 地址 | `YOOX_MINIO_EXTERNAL_ENDPOINT` | 设备必须能访问，Nano 默认服务端口通常为 `9100` |
| WebRTC 地址 | `YOOX_WEBRTC_ADDITIONAL_HOSTS` | 多网卡时填写浏览器可能使用的地址，多个值使用逗号分隔 |
| 服务端口 | `YOOX_HTTP_PORT`、`YOOX_PILOT_PORT`、`YOOX_MQTT_PORT`、`YOOX_PUBLIC_RTSP_PORT` | 同步检查防火墙、客户端地址和端口占用 |
| 媒体传输 | `YOOX_RTSP_TRANSPORTS`、`YOOX_RTP_PORT`、`YOOX_RTCP_PORT`、`YOOX_WEBRTC_ICE_PORT` | Nano 通常使用 `udp,tcp`；变更后重新验证直播首帧 |
| 镜像版本 | `YOOX_VERSION` | Nano 必须已离线导入对应版本镜像，不能直接在线拉取 |
| 运行参数 | `YOOX_LOG_LEVEL`、`YOOX_JAVA_OPTS` | 先通过合并配置检查确认 Nano override 是否覆盖该值 |
| 设备接入 | `YOOX_CLOUD_APP_ID`、`YOOX_CLOUD_APP_KEY`、`YOOX_CLOUD_APP_LICENSE` | 属于敏感凭据，修改后验证设备登录和 MQTT 上线 |
| 服务凭据 | 数据库、Redis、MQTT、MinIO、JWT 相关变量 | 不能当作普通配置直接改值，必须按凭据轮换方案同步服务端数据和所有依赖方 |

尤其不要只修改已有数据卷对应的 `YOOX_DB_PASSWORD` 或 `YOOX_DB_ROOT_PASSWORD`。MySQL 初始化变量
只在首次创建数据目录时生效，直接改 `.env` 会导致应用无法登录数据库。

### 4.4 校验配置

保存后执行：

```bash
chmod 600 .env

docker compose \
  --env-file .env \
  -f compose.yml \
  -f compose.nano.yml \
  config --quiet
```

没有输出且命令返回提示符，表示 Compose 配置语法通过。不要在共享终端或工单中执行不带
`--quiet` 的 `docker compose config`，因为完整输出可能包含已经展开的密码和密钥。

语法通过不代表地址、账号或 License 一定有效，仍需执行变更后的业务验收。

### 4.5 应用配置

应用配置会重建受影响的容器。执行前必须安排维护窗口，并确认：

- 所有飞机已经安全落地；
- 没有正在执行的航线、返航、降落或点飞；
- 没有正在建立或使用的 DRC 会话；
- 现场人员可以接管。

确认安全后执行：

```bash
docker compose \
  --env-file .env \
  -f compose.yml \
  -f compose.nano.yml \
  up -d --wait --wait-timeout 300
```

Compose 会比较合并后的配置，只重建配置发生变化的服务。修改 `.env` 后不要只执行
`docker compose restart`；`restart` 不会用新环境变量重新创建容器。

### 4.6 变更后验收

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml ps --all
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:19000/actuator/health
curl -fsS http://127.0.0.1:8081/healthz
```

随后按实际变更验证：

1. Web 可以登录；
2. 遥控器能够登录并连接 MQTT；
3. 设备拓扑和 OSD 持续更新；
4. 修改媒体配置时验证 RTSP 推流和浏览器首帧；
5. 修改对象存储配置时验证文件上传与下载；
6. 涉及远控时只在批准的安全测试条件下验证 DRC。

### 4.7 配置回滚

先查看备份：

```bash
ls -lt .env.bak.*
```

选择正确的备份并恢复，下面的文件名需要替换为实际文件名：

```bash
cp -p .env.bak.YYYYMMDD-HHMMSS .env
chmod 600 .env

docker compose --env-file .env -f compose.yml -f compose.nano.yml config --quiet
docker compose --env-file .env -f compose.yml -f compose.nano.yml up -d --wait --wait-timeout 300
docker compose --env-file .env -f compose.yml -f compose.nano.yml ps --all
```

回滚同样会重建受影响的容器，也必须遵守飞行安全维护窗口。

## 5. 服务启停和重建

以下操作都在项目目录执行，并遵守第 4.5 节的安全检查。

启动或更新整套服务：

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml up -d --wait --wait-timeout 300
```

只重启单个服务，且不重新加载环境变量：

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml restart api
```

停止容器但保留容器、网络和数据卷：

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml stop
```

重新启动已经停止的容器：

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml start
```

删除容器和项目网络但保留命名卷：

```bash
docker compose --env-file .env -f compose.yml -f compose.nano.yml down
```

普通维护禁止使用：

```bash
docker compose down -v
```

`-v` 会删除 MySQL、Redis、MinIO 和监控数据卷，可能造成不可恢复的数据丢失。

## 6. 备份与更新

修改配置或升级前，至少备份 `.env`、数据库和对象存储。数据库备份应保存在项目目录之外：

```bash
BACKUP_DIR=/home/jetson/backups/yoox-cloud-gcs
mkdir -p "$BACKUP_DIR"
chmod 700 "$BACKUP_DIR"

docker compose --env-file .env -f compose.yml -f compose.nano.yml exec -T mysql \
  sh -ec 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysqldump -uroot "$MYSQL_DATABASE" --single-transaction --routines --events' \
  > "$BACKUP_DIR/mysql-$(date +%Y%m%d-%H%M%S).sql"
```

MinIO 数据应使用 `mc mirror` 备份到另一块磁盘或另一台主机。只复制正在运行的 MySQL Docker
卷不能保证数据库一致性。

Nano 的离线更新、镜像导入和版本回滚必须按照
[Nano 完全离线快速部署](13-Nano快速部署.md) 的“离线更新”和“回滚”章节操作。不要在 Nano 上执行
`docker compose pull`，也不要使用 `latest` 镜像。

## 7. 常见问题

| 现象 | 检查和处理 |
| --- | --- |
| `Couldn't find env file: /home/jetson/.env` | 当前目录错误；先执行 `cd /home/jetson/yoox-cloud-gcs` |
| 离线安装停在 4/6，提示 `change_me / replace_with` | 修改日志所列的部署目录 `.env`；已有部署不会重新读取 `.env.template`，见下方 7.1 |
| 修改 `.env` 后配置没有生效 | 确认使用了两个 Compose 文件，并执行 `up -d`；不要只执行 `restart` |
| 容器 `unhealthy` 或反复重启 | 先执行 `ps --all` 和对应服务的 `logs --tail=200`，再检查磁盘、内存、端口及依赖服务 |
| Docker 无法连接 | 检查 `systemctl status docker` 和用户 Docker 权限 |
| Web 返回 502 | 检查 `api`、`mysql`、`redis` 健康状态以及 Web/API 日志 |
| 遥控器或设备不上线，或连接成功后马上断开 | 优先检查 Nano 联网、默认路由、DNS、实际时钟/NTP 和外网依赖；再检查 9000/1883、EMQX、License 和 MQTT 凭据。2026-10-21 曾出现 Nano 联网后断连消失的现场案例，详见[遥控器云服务频繁断连排查](09-遥控器云服务频繁断连排查.md) |
| RTSP 推流无画面 | 检查 MediaMTX 日志、8554、8000、8188/8189 端口和对外地址 |
| 控制指令超时或 `211001` | 参见[指令链路诊断日志指南](14-指令链路诊断日志指南.md)和[MQTT 直连 A/B 测试指南](15-MQTT直连AB测试指南.md) |
| 磁盘空间不足 | 执行 `df -h` 和 `docker system df`；先转移备份和日志，不要直接清理数据卷 |

### 7.1 离线安装停在 4/6：配置仍含占位值

适用于 x86_64 和 Nano 离线包。典型输出：

```text
=== [4/6] 校验配置 ===
Offline map installed: china-20261020-v1
ERROR: Replace every change_me/replace_with value in .env.
```

这是本地配置的占位符检查失败；地图安装已经成功，该报错不表示设备授权被拒绝。
新版校验脚本会显示实际 `.env` 的绝对路径、未填写项的行号和变量名，不输出密码。

**为什么修改模板后重跑仍失败**

| 文件 | 使用时机 |
| --- | --- |
| 离线包目录的 `.env.template` | 仅在部署目录尚无 `.env` 的首次安装中复制 |
| 部署目录的 `.env` | 后续校验、容器启动和更新实际读取的配置 |

首次安装会先创建 `.env`，然后才校验；即使校验失败，文件也不会删除。
再次执行 `install.sh` 时，只要发现 `.env` 已存在，就自动进入更新模式，保留现场配置和密码，
仅更新其中的 `YOOX_VERSION`。因此后来只修改 `.env.template`，不会修复已生成的 `.env`。
这也意味着重跑时传入不同 IP 不会自动修改已有 `YOOX_PUBLIC_HOST`。

部署目录取决于运行脚本的 `$HOME`，以安装日志为准：普通用户可能是
`/home/a207/yoox-cloud-gcs`，root/sudo 安装可能是 `/root/yoox-cloud-gcs`。
安装包在 `/home/a207/`，并不意味着实际部署也在该目录。

**修复步骤**

1. 进入日志显示的实际部署目录，确认文件存在再操作。以下是 root 部署示例；普通用户部署请替换目录并使用原安装用户。

   ```bash
   sudo -i
   cd /root/yoox-cloud-gcs
   pwd
   ls -l .env compose.yml
   cp -p .env ".env.bak.$(date +%Y%m%d-%H%M%S)"
   grep -nE '=(.*change_me|replace_with)' .env | cut -d= -f1
   ```

   最后一条命令只显示行号和变量名。不要输出或发送完整密码配置。

2. 执行 `nano .env`，补齐列出的占位值。若模板已填写，可从模板按变量名逐项复制对应值。
   不要整份覆盖 `.env`，以免覆盖部署 IP、镜像版本和原有凭据；也不要删除 `.env` 或数据卷来强制首次安装。
   已有 MySQL 数据卷时必须沿用原数据库凭据，不能仅修改环境变量来重置密码。
   JWT 密钥至少 32 字符，可选 TURN、Grafana 配置中的占位值也需处理。
   仓库 Nano 交付中的 `local_dev_app_id`、`local_dev_app_key`、`local_dev_license` 是本地开发值，
   不能把占位符校验通过当作正式授权或真机接入已经验证。

3. 保存后，在部署目录重新校验，并核对实际对外地址：

   ```bash
   bash scripts/preflight.sh .env
   grep '^YOOX_PUBLIC_HOST=' .env
   ```

   应看到 `YOOX Cloud GCS preflight passed.`。IP 必须是设备实际可达的服务器地址；
   “传入 IP 不是当前网卡 IP”的警告与本次占位符错误是两个独立问题。

4. 校验通过后，以原安装用户回到完整离线包目录重跑原安装命令，并保留可选 profile 参数。
   如果 x86_64 部署的镜像加载、配置复制和地图安装都已成功，也可直接在部署目录继续第 5、6 步：

   ```bash
   docker compose --env-file .env up -d --no-build --pull never --remove-orphans --wait --wait-timeout 300 &&
   bash scripts/smoke-test.sh .env
   ```

   上述单文件启动命令适用于 Linux x86_64；Nano 应通过原安装脚本叠加 `compose.nano.yml`，
   Windows 手工部署应保留原 Windows override。可选服务也必须保留原 profile 设置。
   已运行环境的重建操作遵循本文 4.5 节的维护要求。

现场使用的 Python 同步修复与手动编辑原理相同：只把部署 `.env` 中仍含占位值的项目从已填写模板补齐，
其余配置保留。随后运行的 `preflight.sh` 和 `docker compose up` 正是安装脚本的第 4、5 步，
没有绕过校验。校验通过后还需完成烟雾测试和对应业务验收。

## 8. 安全要求

- `.env` 权限保持为 `600`，不得提交到 Git 或对外发送；
- 不在命令行参数、截图和日志中暴露密码、JWT、MQTT 或 MinIO 凭据；
- 远程维护优先使用 SSH 密钥、VPN 或 [Tailscale](17-Tailscale异地访问指南.md)；
- 管理端口默认只允许本机访问，不要直接暴露到公网；
- 不执行 `docker compose down -v`；
- 不在离线 Nano 上执行 `docker system prune -a`，否则可能删除回滚所需镜像；
- 所有会重启服务的维护都必须先确认飞行安全状态；
- 变更后必须检查容器健康，并完成与变更范围对应的业务验收。

## 可选 RTSP 低码率转码

x86 Linux 可显式叠加 `compose.transcode.yml`，使用独立 FFmpeg 容器发布 `-low` 流。
默认最高 720p、25 fps、目标 1500 kbps，限制 2 核 CPU / 768 MB 内存，不新增端口或卷。
输入路径及 `YOOX_TRANSCODE_*` 参数见 [RTSP 低码率转码服务](21-RTSP低码率转码服务.md)。
该服务默认不启动，使用现有 RTSP 发布凭据，未纳入现有离线镜像包。
